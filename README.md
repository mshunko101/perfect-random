## Что это

**perfect_random (CascadePRNG)** — каскадный генератор псевдослучайных чисел с нелинейной архитектурой и пермутацией ролей компонент. Один header-only файл, два движка, внешних зависимостей нет:

| Движок | Модуль | Полезных бит | Назначение |
|:---|:---:|:---:|:---|
| `cascade_prng` | `M = 2^31 - 1` | 31 | Симуляции, игры, STD-алгоритмы |
| `cascade_prng64` | `M = 2^61 - 1` | 61 | Монте-Карло, высокая точность |

Вывод честно урезан: все движки выдают значения из `[0, M-1]`. Старший бит у 31-битного движка и три старших у 61-битного всегда нулевые — интерфейс (`min()`/`max()`) это отражает и ничего не скрывает.

## Две версии генератора

Ядро у обеих версий одно и то же — каскад из трёх компонент с квадратичной нелинейностью и пермутацией ролей. Различие — в одном слагаемом квадратичного члена:

| | **Версия 1 — статистическая** | **Версия 2 — с обратной связью** |
|:---|:---|:---|
| Ядро шага | `c = (c² + a + b) mod M` | `c = (c² + a + b + fb) mod M`, где `fb = mix64(prev_out) >> 48` |
| Обратная связь | нет | усечённая, 16 бит через splitmix64-финалайзер |
| Период | аналитическая оценка: `T = 3 · lcm(ord(A), ord(B))` | аналитической оценки нет — отображение необратимо, возможны аттракторы |
| Цена шага | базовая | + один `mix64` на шаг (~15–20% дороже) |
| Воспроизводимость | да; сериализация `a, b, c, counter, out_idx, N` | да; сериализация `a, b, c, prev_out, counter, out_idx, N` |
| Когда выбирать | массовые симуляции, игры — где важны скорость и теоретически обоснованный период | когда нужно усложнить аналитическое моделирование потока и не жалко скорости |

> **Про имена классов.** В актуальном заголовке (версия 2) обратная связь встроена прямо в `cascade_prng` и `cascade_prng64` — отдельных классов `cascade_prng_fb` / `cascade_prng64_fb` в C++-интерфейсе нет. Статистическое поведение соответствует версии 1. Форматы сериализации версий 1 и 2 **несовместимы**: в версии 2 в состояние добавлен `prev_out`.

## Как работает

### Каскадная динамика

Три внутренних переменных `(a, b, c)` — целые числа в диапазоне `[1, M-1]`, где `M` — простое число Мерсенна. На каждом шаге:

- **`a`** — затухание: `a = (a * 5/9) mod M` (обратный элемент по модулю M);
- **`b`** — рост: `b = (b * 5/3) mod M`;
- **`c`** — нелинейность: `c = (c² + a + b [+ fb]) mod M` — квадратичный член исключает раскрытие последовательности матричным анализом, в отличие от LCG, MRG и Mersenne Twister.

Множители `5/9` и `5/3` заданы математической моделью каскада, а не подобраны эмпирически.

### Пермутация ролей

Каждые `N` шагов происходит циклический сдвиг ролей: `(a, b, c) → (c, a, b)`. Переменная, бывшая затуханием, становится нелинейностью; нелинейность — ростом; рост — затуханием. После трёх пермутаций роли возвращаются к исходным. Пермутация меняет **роли операций**, а не данные или биты.

По умолчанию `N = 49`.

### Обратная связь (версия 2)

Выход предыдущего шага проходит через финалайзер splitmix64, его верхние 16 бит входят в квадратичный член:

```
fb = mix64(prev_out) >> 48
c  = (c² + a + b + fb) mod M
```

Это делает шаг необратимым: для точного отката назад пришлось бы перебирать `2^16` вариантов на каждом шаге. Важно понимать границы этого механизма:

- обратная связь **не добавляет криптостойкости** — `prev_out` является частью публичного потока, и наблюдатель вычисляет `fb` сам, точно и без перебора;
- обратная связь **не добавляет энтропии** — ГПСЧ в принципе не может этого делать;
- оценка периода `T = 3 · lcm(ord(A), ord(B))`, действительная для версии 1, для версии 2 **более недействительна**: отображение стало необратимым, возможны аттракторы. Фактический период измеряется эмпирически (см. «Ограничения»).

### Вывод и инициализация

```
output = (a * b + c) mod M
```

Инициализация (версия 2) — прямое заполнение состояния (`seed_words`): каждый компонент получает собственное перемешанное слово, потолка энтропии «сид срезается до `s mod M`» нет. Прогрев `discard(N)` после сидирования размазывает линейность инициализации по состоянию.

Три способа сидирования:

1. **Один сид** — `seed(s)`: слова состояния = `mix64(s ^ K0)`, `mix64(s ^ K1)`, `mix64(s ^ K2)`;
2. **Два сида** — `seed(s1, s2)`: для смешивания независимых источников энтропии (`random_device` + время и т. п.);
3. **SeedSequence** — буфер раскладывается на три независимых слова состояния, ни одно слово не теряется.

Сид `0` заменяется на `1`; нулевые `a`, `b`, `c` защищены — ни одна из компонент не вырождается.

## Интерфейс (C++17 / C++20)

Оба движка реализуют полный контракт URBG (`std::uniform_random_bit_generator` на C++20 закреплён `static_assert`):

- `min()` / `max()` / `result_type` / `operator()` — работает с `std::uniform_int_distribution`, `std::uniform_real_distribution`, `std::shuffle` из коробки;
- конструкторы и `seed()` для арифметического сида, пары сидов и для любого SeedSequence (`std::seed_seq` и свои);
- `generate()` → `double` в `[0, 1)`, `generate_raw()` → целое, `generate_raw_block(dst, n)` — блочная заливка;
- `discard(n)` — пропуск значений без материализации;
- `operator==` / `operator!=` по полному состоянию, `operator<<` / `operator>>` — сериализация состояния (в версии 2 формат включает `prev_out`).

## Использование

### 31 бит, STD-алгоритмы

```cpp
#include "perfect_random.hpp"

using namespace perfect_random;

int main() {
    cascade_prng rng(40);                    // N = 49 по умолчанию

    std::vector<int> v = {1, 2, 3, 4, 5};
    std::uniform_int_distribution<int> d(0, 9);
    int x = d(rng);                          // STD из коробки

    std::shuffle(v.begin(), v.end(), rng);   // и shuffle тоже

    double   val = rng.generate();           // [0.0, 1.0)
    uint32_t raw = rng.generate_raw();       // [0, M-1]
}
```

### 61 бит, Монте-Карло

```cpp
cascade_prng64 rng64(40);

double   val = rng64.generate();       // [0.0, 1.0), 53 бита мантиссы double
uint64_t raw = rng64.generate_raw();   // сырой вывод в [0, M-1]
```

### Два независимых сида

```cpp
std::random_device rd;
cascade_prng64 g64(rd(), std::chrono::steady_clock::now().time_since_epoch().count());
```

`s1` и `s2` должны приходить из независимых источников — иначе смешивание ничего не даёт.

### SeedSequence

```cpp
std::seed_seq seq{1, 2, 3, 4, 5};
cascade_prng gs(seq);
```

### Сохранение и восстановление

```cpp
cascade_prng a(40);
std::stringstream ss;
ss << a;                              // a, b, c, prev_out, counter, out_idx, N

cascade_prng b;
ss >> b;                              // b == a — точная воспроизводимость
```

### C API

```c
#include "perfect_random_c.h"

cascade_prng_rng g;
cascade_prng_init(&g, 40, 49);

double   val = cascade_prng_generate(&g);
uint32_t raw = cascade_prng_generate_raw(&g);

cascade_prng_discard(&g, 1000);
```

C-версия полностью паритетна C++: оба движка, `discard`, блочная генерация, `reset`, `equals`, геттеры состояния.

## Сборка и тесты

Header-only — достаточно положить `perfect_random.hpp` (C++) или `perfect_random_c.h` (C) в проект.

Тесты и бенчмарк — в одном файле `cpp_tests.cpp` (30 тестов по 2 движкам + скоростной бенчмарк против `mt19937_64`, вся генерация через STD-интерфейс):

```bash
# GCC / Clang
g++ -std=c++17 -O2 -Wall -Wextra -o cpp_tests cpp_tests.cpp && ./cpp_tests

# MSVC
cl /std:c++17 /O2 cpp_tests.cpp

# серьёзный замер производительности
./cpp_tests 1000000000
```

Код возврата зависит только от тестов — бенчмарк не «роняет» прогон в CI.

## Производительность

Бенчмарк: 1 000 000 000 сэмплов, MSVC `/O2`, x64, best of 3, прогрев.

| Генератор | нс/вызов | млн/сек | ГБ/сек |
|:---|:---:|:---:|:---:|
| CascadePRNG (C++) | 10.80 | 92.6 | 0.74 |
| CascadePRNG (C) | 10.95 | 91.3 | 0.73 |
| mt19937_64 + dist | 6.14 | 162.8 | 1.30 |

Цифры сняты до объединения реализаций в один заголовок и до добавления обратной связи — после этих изменений их стоит перемерить. Актуальные цифры будут добавлены по факту замера.

`mt19937_64` быстрее в ~1.7 раза: его ядро — сдвиги и XOR, тогда как CascadePRNG выполняет 4 операции `% M` на вызов. Компромисс: нелинейная архитектура и пермутация ролей требуют больше вычислений. C++ и C версии идут ноздря в ноздрю — overhead абстракций отсутствует.

## Криптографическая оценка

**Ни одна из конфигураций не является криптографическим ГПСЧ.** Это сказано в первой строке, и это не оговорка ради приличия.

- **`cascade_prng` (31 бит).** Пространство состояний ~2^31, наивное восстановление по двум выходам стоит порядка 2^31 операций — секунды на современном железе. Против целенаправленного анализа движок не защищает. Для игр и симуляций — да; для чего-либо ещё — нет.
- **`cascade_prng64` (61 бит).** Простейшая известная нам атака — восстановление состояния по двум последовательным выходам перебором порядка 2^61 квадратных решений. Это граница **одной наивной атаки**, а не оценка криптостойкости: встреча посередине и другие методы не исключены, формальный криптоанализ не проводился.
- **Обратная связь — не шифрование.** `fb` вычисляется наблюдателем из публичного потока, поэтому версия 2 не даёт ни бита дополнительной защиты от восстановления состояния по сравнению с версией 1. Её роль — усложнить аналитическое моделирование статистической структуры потока.
- **Не источник энтропии.** ГПСЧ детерминирован и не создаёт новую энтропию — он лишь распределяет энтропию сида. Для криптографии: истинный источник энтропии (`/dev/urandom`, аппаратные ГСЧ) плюс криптостойкий ГПСЧ (ChaCha20, HMAC-DRBG и подобные).

| Сценарий | Статистическая | С обратной связью | Криптография |
|:---|:---:|:---:|:---|
| Симуляции, Монте-Карло | ✅ | ✅ | ❌ |
| Игры, STD-алгоритмы | ✅ | ✅ | ❌ |
| Ключи, nonce, инициализация криптоалгоритмов | ❌ | ❌ | ✅ — ChaCha20/HMAC-DRBG от истинного источника энтропии |

## Ограничения и известные нюансы

- **Не криптография** — см. раздел выше.
- **Период версии 2 не оценён аналитически.** Для версии 1 действует оценка `T = 3 · lcm(ord(A), ord(B))`. Для версии 2 отображение необратимо, и гарантий длины периода нет — требуется эмпирический замер (поиск цикла по полному состоянию).
- **Статистические батареи — впереди.** Актуальные результаты прогонов через TestU01, PractRand и DieHarder будут добавлены в этот README по факту.
- **Не квазислучайный** — Соболь и Холтона не заменяет.
- Для статистических батарей 31/61-битный поток следует упаковывать плотно (бит к биту), иначе «мёртвые» старшие биты дадут фейл на формате файла, а не на генераторе.
- Формат сериализации версии 2 включает `prev_out` и несовместим с сохранёнными состояниями версии 1 и ранних релизов.
